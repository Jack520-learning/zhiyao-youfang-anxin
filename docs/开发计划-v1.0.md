# 老人安全用药 AI Web 应用开发计划

> 依据：[需求文档 V1.0](./需求文档-v1.0.md)  
> 计划版本：V1.0  
> 制定日期：2026-11-14  
> 目标：在正式发布前完成可运行、可演示、可审查的 AI Web 最小完整产品

---

## 1. 开发目标

V1 不追求覆盖所有老人健康场景，而是打通三条完整闭环：

1. **拍照加药**：拍照留存 → OCR/识别适配 → 人工确认 → 风险核查 → 入档。
2. **安全问药**：语音/文字提问 → Agent 任务编排 → 本地规则 + RAG → 分级回答 → 来源展开。
3. **提醒协同**：定时提醒 → 老人确认状态 → 漏服风险分支 → 家属跨设备摘要。

所有核心数据必须本地持久化，并在跨设备场景通过轻量同步服务保持一致。

---

## 2. 技术路线

| 层级 | V1 方案 | 说明 |
|---|---|---|
| 前端框架 | React + TypeScript + Vite | 组件化、类型安全、构建简单 |
| 路由 | React Router | 老人端和家属端独立路由 |
| 状态管理 | Zustand + IndexedDB | 关键业务状态可恢复 |
| 样式 | 原生 CSS Design Tokens | 控制适老化字体、对比度和触控尺寸 |
| PWA | Manifest + Service Worker + Web Push | 安装、离线壳和系统通知 |
| 规则引擎 | TypeScript 本地规则 + JSON 演示知识库 | 保障离线安全和可测试性 |
| AI 服务 | Node HTTP 服务，可选 OpenAI 兼容 API | 无密钥时使用可复现规则演示模式 |
| 跨设备同步 | Node 服务 + 本地 JSON 数据仓 | 原型级家庭同步，后续可替换数据库 |
| 测试 | Vitest + 浏览器验收 | 规则、数据持久化和关键交互 |

V1 原型不存储真实老人数据。正式部署前必须补账号认证、数据库、HTTPS、安全审计和医疗内容审核。

## 5. 关键验收用例

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AC-01 | 刷新恢复 | 已确认药物和未完成拍照草稿均能恢复 |
| AC-02 | 低置信 OCR | 未确认前不能进入有效用药清单 |
| AC-03 | 重复成分 | 返回中危结果、触发字段和来源 |
| AC-04 | 高危问药 | 不输出停药、调剂量或双倍补服 |
| AC-05 | 无资料问药 | 明确说明资料不足并建议咨询专业人员 |
| AC-06 | 漏服状态 | 未操作显示“尚未确认”，不直接算漏服 |
| AC-07 | 家属同步 | 两端同码后能读取同一份授权摘要 |
| AC-08 | 家属隐私 | 家属端没有完整老人对话 |
| AC-09 | 通知降级 | 通知权限被拒绝时仍显示页面内提醒和恢复入口 |
| AC-10 | 数据删除 | 本地档案被清除并通知服务端删除 |

## 7. 风险控制

- 优先保证完整闭环和稳定演示，不在提交前扩展诊断或复杂预测。
- 无 AI 密钥时保留确定性规则演示模式，避免现场网络导致作品不可用。
- 原型知识库只用于交互和技术验证，正式发布前必须由医药专业人员审核。
- 跨设备原型使用连接码，正式环境必须升级为账号认证和细粒度授权。
- 关闭页面通知受浏览器权限和 HTTPS 限制，演示时准备页面内降级路径。
- 物理 SOS、自动拨打 120/110 不作为 V1 已实现承诺。
