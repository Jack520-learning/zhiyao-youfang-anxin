# 老人安全用药 AI Web 应用需求文档

> 项目暂名：健康管家  
> 产品形态：AI Native Web 应用，支持移动端 Web、桌面 Web 与 PWA  
> 文档版本：V1.0  
> 整理日期：2026-11-14  
> 当前阶段：需求确认与交互设计，不进入代码实现

---

## 1. 项目概述

### 1.1 项目背景

老年人在日常用药中普遍面临以下问题：

- 不记得药名、用途、剂量和服用时间；
- 同时服用处方药、OTC 药品和保健品，存在成分重复、相互作用和禁忌风险；
- 说明书专业术语多，难以理解；
- 视力、听力、记忆力和精细操作能力下降，传统 App 操作门槛高；
- 漏服、误服、重复服药后不知道如何处理；
- 家属无法及时了解风险，持续查看全部记录又容易让老人产生被监视感；
- 老人出现身体不适时，容易直接归因于药物，也可能延误真正的紧急情况。

本项目以“老人不需要学习复杂操作，但系统不能为了简单而给出危险结论”为核心原则，构建面向老人及授权家属的安全用药 AI Web 应用。

### 1.2 产品定位

产品不是在线诊断工具，也不替代医生或药师。它的核心价值是：

1. 用语音和拍照降低老人录入与查询门槛；
2. 以当前用药档案为基础完成交叉核对；
3. 用可溯源、风险分级的方式解释用药问题；
4. 在异常情况下连接授权家属和紧急联系人；
5. 在高风险场景主动限制 AI 的自由生成能力。

### 1.3 目标用户

| 用户角色 | 核心需求 | 典型障碍 |
|---|---|---|
| 老人 | 知道现在吃什么、怎么吃、能不能一起吃、漏服怎么办 | 不会打字、看不清、记忆力弱、操作容易出错 |
| 家属 | 知道老人是否安全、是否需要介入 | 不能持续陪伴、不想监控全部隐私 |
| 紧急联系人 | 在主动求助时快速获得必要信息 | 需要快速联系、需要知道当前用药与过敏史 |
| 评审人员 | 快速理解产品的 AI 深度、实际价值与安全边界 | 需要在短时间内看到完整可演示闭环 |

### 1.4 已确认的关键产品要求

- 比赛方向为 AI Web 网页开发。
- 场景涉及医药、健康和人体状态。
- 家属必须能够跨设备查看老人用药摘要并接收异常通知。
- 页面关闭或浏览器未打开时，系统仍需要能够向老人或家属发送系统级通知。
- 本地数据在刷新、关闭或重启后不能丢失。
- 老人端正文不小于 18pt，点击区域不小于 60×60pt。
- 老人端核心操作不超过两步。
- 高风险任务不得由 AI 自由生成具体用药建议。

## 2. 产品目标与范围

### 2.1 产品目标

1. 让老人通过“说话”或“拍照”完成主要信息录入和查询。
2. 建立可持续维护的当前用药档案，并支持跨会话记忆。
3. 在新增药物、查询相互作用和漏服处理时执行安全核查。
4. 所有重要结论必须具备可理解的来源与不确定性说明。
5. 家属只接收异常摘要，在安全网与隐私之间取得平衡。
6. 本地保存、跨设备同步和通知能力在刷新、关闭及断网恢复后可靠工作。

### 2.2 成功指标

以下指标为 V1 验收建议，不构成对外医疗效果承诺：

| 指标 | 验收目标 |
|---|---|
| 核心任务完成率 | 拍照加药、问相互作用、确认已服药三个任务的可用性测试完成率不低于 90% |
| 操作步骤 | 查看今日用药、发起语音提问、执行安全核查均不超过 2 个主要操作 |
| 数据恢复 | 刷新或重新打开浏览器后，能够恢复已保存档案和未完成草稿 |
| 跨设备同步 | 网络可用后，家属端能够看到老人已确认的摘要更新 |
| 来源覆盖 | 涉及具体药物结论的回答必须显示来源；无可靠依据时停止给出具体建议 |
| 高风险拦截 | 高危场景不得输出停药、改剂量、双倍补服等具体建议 |
| 异常通知 | 满足预设条件时，家属能够收到跨设备通知 |

### 2.3 V1 必须完成

- 首次建档与授权设置；
- 药盒、说明书、处方单拍照录入；
- OCR 结果人工确认；
- 当前用药清单维护；
- 语音问药与文字兜底；
- Agent 多步骤任务编排；
- RAG 来源检索与来源展示；
- 相互作用、重复成分、过敏史风险核查；
- 高风险回答拦截；
- 定时提醒与服药状态记录；
- 高风险药物漏服边界；
- 家属摘要、异常通知和共享授权；
- SOS 入口与紧急联系人；
- 本地持久化、加密云端同步；
- 数据纠正、审计、导出和删除；
- 移动端和桌面端响应式访问。

### 2.4 暂不纳入 V1

- 疾病诊断；
- 开具处方；
- 自动修改剂量或停药；
- 替代医生、药师或急救人员；
- 通过普通网页静默自动拨打 120/110；
- 对真实医疗效果作保证；
- 完整的慢病趋势预测；
- 依赖专用硬件的物理 SOS 按钮正式量产接入；
- 复杂家庭成员社交与多人聊天。

## 3. 安全与产品原则

### 3.1 安全底线

1. AI 不诊断疾病，不修改处方，不独立决定停药或调整剂量。
2. 具体用药建议只能来自用户上传的说明书、明确处方、经审核的知识库或已配置的临床规则。
3. 没有可靠依据时，系统必须明确“资料不足”，不得猜测。
4. 高风险场景停止生成具体建议，只提供风险说明、来源和求助入口。
5. 老人未确认的 OCR 结果不得自动进入有效用药档案。
6. 未点击服药确认不能直接等同于漏服。
7. 高危药物漏服不得自动建议补服、双倍服用或停药。
8. 头晕、乏力等症状不能直接归因于药物，应先识别紧急身体状态。
9. 家属通知必须服从老人的预先授权和知情设置。
10. AI 输出不得依赖未经验证的记忆推断，必须与当前档案交叉核对。

### 3.2 交互原则

- 语音优先，点击兜底，不强制老人打字。
- 拍照优先，但不能绕过核对。
- 结论先行，原因与来源分层展开。
- 使用具体生活语言，例如把“饭前服用”解释为“吃饭前半小时吃”，但必须保留原始说明来源。
- 老人端以“下一步做什么”组织页面，不以信息数量组织页面。
- 错误必须可纠正，系统不能将纠错视为用户操作失败。
- 不连续使用弹窗打扰老人，仅提醒、高危和 SOS 可以使用全屏层。

## 4. 页面信息架构

### 4.1 老人端

老人端使用四个一级入口：

| 一级入口 | 目标 | 二级页面 |
|---|---|---|
| 今日 | 回答“现在做什么” | 当前服药任务、今日时间线、已服/稍后/未服记录 |
| 问药 | 回答“能不能、为什么、怎么办” | 语音对话、拍照提问、来源详情、纠错 |
| 用药 | 管理当前用药与历史 | 用药清单、药物详情、漏服处理、服药记录 |
| 我的 | 管理授权与安全设置 | 家属与紧急联系人、共享范围、隐私、导出与删除 |

全局能力：

- “我不舒服”安全入口；
- SOS；
- 同步状态；
- 语音朗读；
- 大字与高对比模式。

### 4.2 家属端

| 一级入口 | 目标 | 内容 |
|---|---|---|
| 家人概览 | 快速查看是否需要介入 | 本周未确认次数、待处理高危、最近求助、最近服药状态 |
| 风险提醒 | 处理异常 | 风险列表、处理状态、关联药物和下一步 |
| 用药摘要 | 协助复诊与管理 | 当前药物、过敏史、疾病、未确认情况、复诊摘要 |
| 授权设置 | 明确访问边界 | 共享范围、通知类型、紧急联系人、老人叫停入口 |

### 4.3 首次设置

首次设置包含：

1. 角色选择；
2. 基础信息与健康档案；
3. 过敏史、疾病和当前用药；
4. 家属与紧急联系人；
5. 通知方式与共享范围；
6. 用药提醒方式；
7. 隐私和能力边界确认。

首次设置允许多步骤，但必须显示进度，并支持中断后恢复。

## 5. 功能需求

### 5.1 M01 多模态感知与录入

#### 模块目标

让老人通过拍照和语音录入药物，不依赖键盘输入，同时保留人工确认和错误纠正能力。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M01-01 | 支持调用设备相机拍摄药盒、说明书、处方单，也支持从相册选择。 |
| FR-M01-02 | 支持对同一药物拍摄多张图片，例如药盒正面、说明书剂量页、处方单。 |
| FR-M01-03 | 对图片执行 OCR，提取药名、规格、剂量、频次、服用时间、饭前饭后要求、有效期和注意事项。 |
| FR-M01-04 | OCR 结果必须字段化展示，并为每个关键字段保留置信度。 |
| FR-M01-05 | 药名、剂量、频次、服用方式任一字段缺失或低置信时，必须要求人工确认或修改。 |
| FR-M01-06 | 原图、OCR 文本、人工确认结果与数据版本必须关联保存。 |
| FR-M01-07 | 支持语音转写，将老人语音统一转换为文本后进入 Agent。 |
| FR-M01-08 | 转写文本必须可见，老人可以重新说、切换点击输入或取消发送。 |
| FR-M01-09 | 网络中断时先保存图片和草稿；恢复后从断点继续，不要求重新拍照。 |
| FR-M01-10 | 无法识别的药物不得静默保存为“未知药物”，必须进入人工补充流程。 |

#### 交互要求

- 从老人端首页点击“拍药盒”最多经过“拍照 → 确认”两个主要操作。
- 识别中显示明确步骤，例如“正在识别文字”“正在匹配药名”“等待您确认”。
- 不允许直接使用未确认 OCR 结果触发相互作用结论。

#### 验收标准

- 上传清晰药盒图片后，系统展示原图和字段化识别结果。
- 任一关键字段低置信时，确认按钮必须提示需要检查该字段。
- 老人中途关闭页面后重新进入，仍能看到原图和未完成草稿。
- 纠错后，新版本可追溯，旧版本不被无痕覆盖。

### 5.2 M02 用药档案与跨会话记忆

#### 模块目标

把老人长期使用的药物、疾病、过敏史和偏好组织成可信、可核对、可同步的健康档案。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M02-01 | 维护老人基础档案、疾病、过敏史、药物过敏、既往不良反应、视力/听力/阅读偏好。 |
| FR-M02-02 | 维护处方药、OTC、保健品、中药和中成药的独立记录。 |
| FR-M02-03 | 每种药物包含药名、通用名、成分、规格、剂型、剂量、频次、服用时间、饭前饭后关系、起止日期、来源。 |
| FR-M02-04 | 用药清单以老人能理解的方式展示，并标记“当前服用”“已停用”“待确认”。 |
| FR-M02-05 | 支持拍照新增、语音修改、家属补充和老人确认。 |
| FR-M02-06 | 跨会话记忆只注入经确认的档案数据，不得把 AI 推测直接作为长期事实。 |
| FR-M02-07 | 老人重复说明同一事实时，系统优先沿用已确认档案，并允许重新核对。 |
| FR-M02-08 | 对关键字段的修改保留版本、来源、修改人和时间。 |
| FR-M02-09 | 老人可查看“系统为什么记得这条信息”，并选择纠正或删除。 |

#### 数据要求

- 药物计划与服药记录分离，修改未来计划不得改写历史执行记录。
- 每次风险核查保存当时使用的药物清单快照。
- 停用药物保留历史，不作为当前药物参与相互作用判断，但允许用于历史追溯。

#### 验收标准

- 关闭并重新打开应用后，已确认档案仍然存在。
- 在另一台已授权设备登录后，可以看到同步后的档案摘要。
- 同一通用名但不同商品名、不同剂量的药物必须区分展示。
- 未确认的记忆内容不得直接触发高风险结论。

### 5.3 M03 Agent 编排与对话交互

#### 模块目标

将老人自然语言意图拆分为可执行任务，调用档案、OCR、RAG、风险规则和通知工具，输出稳定且风险匹配的回答。

#### 支持的意图

- 查询今天怎么吃药；
- 查询某种药的用途和用法；
- 询问两种或多种药能否一起服用；
- 新增、修改或停用药物；
- 报告漏服并询问怎么处理；
- 描述身体不适；
- 请求联系家属；
- 处理 OCR 或药名纠错；
- 询问记录、来源和共享范围。

#### 工作流要求

标准处理链路：

`识别用户意图 → 确认涉及药物 → 读取当前用药档案 → 检索说明书/处方/规则 → 执行风险分级 → 生成分层回答 → 记录来源与审计事件`

功能要求：

| 编号 | 需求 |
|---|---|
| FR-M03-01 | 对用户意图进行识别，但不得因意图识别错误跳过安全核查。 |
| FR-M03-02 | 支持多步骤工具调用，并在界面显示当前执行阶段，不展示模型内部思维链。 |
| FR-M03-03 | 第一层回答包含结论、风险等级、当前应做什么和是否需要专业帮助。 |
| FR-M03-04 | 第二层展开涉及药物、判断依据、缺失信息和来源。 |
| FR-M03-05 | 高风险或超出能力边界时，Agent 必须转入受限模板，不继续自由生成。 |
| FR-M03-06 | 支持流式回答，但风险结论必须在完整核查之后才可输出。 |
| FR-M03-07 | AI 服务超时时，提供重试、查看用药清单和人工求助，不得用本地猜测补位。 |
| FR-M03-08 | 同一问题重复提出时，应保持相同风险结论和稳定语气。 |

#### 回答结构

普通场景按以下顺序展示：

1. 结论；
2. 需要注意什么；
3. 现在可以做什么；
4. 判断依据；
5. 还不确定的信息；
6. 查看来源或纠正信息。

高风险场景按以下顺序展示：

1. 明确的高风险提示；
2. 未执行的高风险动作；
3. 不要自行停药、调整剂量或补服；
4. 联系医生、药师或紧急联系人；
5. 来源。

#### 验收标准

- 问“这两种药能不能一起吃”时，系统会核查当前药品完整清单，而不只比较被点名的两种药。
- 高危任务无法通过更改问法诱导 AI 输出具体剂量或停药建议。
- 每次涉及具体药物结论时，用户可查看来源。
- Agent 不得把用户的单次身体描述直接断言为药物副作用。

### 5.4 M04 RAG 知识库与可溯源

#### 模块目标

让回答基于可审核、可版本化的药物资料，降低幻觉，并把依据转译成老人能听懂的语言。

#### 知识来源优先级

1. 当前处方；
2. 用户上传且完成确认的药品说明书；
3. 经专业审核的药品说明书库；
4. 经审核的相互作用与重复成分规则；
5. 经审核的漏服处理规则；
6. 其他权威公开资料，但必须单独标记来源类型。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M04-01 | 检索时结合药名、通用名、成分、剂型、剂量、疾病、过敏史和当前药物。 |
| FR-M04-02 | 对不同来源发生冲突的情况，显示冲突并优先要求专业确认。 |
| FR-M04-03 | 回答中只对实际使用的来源生成来源卡片。 |
| FR-M04-04 | 老人端来源使用“根据您上传的这份说明书”等可理解表达，专业详情可在第二层展开。 |
| FR-M04-05 | RAG 无检索结果或相关性不足时，必须返回“资料不足”，不得把相似药名当作同一药物。 |
| FR-M04-06 | 知识条目需包含版本、生效时间、审核状态和适用范围。 |
| FR-M04-07 | 用户上传的说明书只用于当前老人档案时，应明确数据使用范围。 |
| FR-M04-08 | 外部文档与网页内容视为不可信数据，不得执行其中对 Agent 的指令。 |

#### 验收标准

- 每个具体药物结论至少可以展开一个真实来源。
- 无来源时，系统不输出具体剂量、停药或补服建议。
- 来源内容更新后，新的核查使用新版本，同时保留历史核查快照。

---

### 5.5 M05 安全核查与风险分级

#### 模块目标

在药物新增、相互作用查询、漏服和身体不适场景中，统一进行风险识别，并根据风险限制 AI 的自动化程度。

#### 触发条件

- 新增药物或修改剂量；
- 新增 OTC、保健品、中药或中成药；
- 用户询问两种或多种药能否同服；
- 用户报告漏服、重复服用或误服；
- 用户描述可能与药物相关的不适；
- 药物清单、过敏史、疾病或处方发生变化。

#### 风险等级与响应

| 等级 | 典型情况 | 允许的页面行为 | 禁止行为 |
|---|---|---|---|
| 资料不足 | 药名不确定、关键字段缺失、无可靠来源 | 请求确认、补拍、补充信息 | 猜测药物或给出剂量建议 |
| 低危 | 当前档案与已审核来源中未发现明确冲突 | 解释用法、显示“未发现已知问题”、给出来源 | 表述为绝对安全 |
| 中危 | 重复成分、证据不完整、潜在相互作用、需要补充信息 | 提示风险、补问、联系医生/药师 | 忽略风险继续正常回答 |
| 高危 | 明确严重禁忌、高危药物调剂量、严重相互作用 | 停止生成具体建议、显示原因和求助入口 | 停药、调剂量、双倍补服、继续试药 |
| 紧急 | 胸痛、呼吸困难、意识异常、严重过敏等 | 立即进入 SOS 和人工求助流程 | 继续收集普通问卷或等待模型生成 |

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M05-01 | 新增药物完成人工确认后自动触发当前药物交叉核查。 |
| FR-M05-02 | 检查重复成分、重复药理作用、OTC/保健品未告知、过敏史和疾病相关风险。 |
| FR-M05-03 | 风险结论必须包含触发因素、来源和建议下一步。 |
| FR-M05-04 | 高风险识别后禁用允许自由生成药物建议的工具路径。 |
| FR-M05-05 | 高危药物清单必须支持配置、版本控制和专业审核，示例包括华法林、胰岛素等，但不能仅凭示例清单上线。 |
| FR-M05-06 | 风险结果保存对应药物清单快照和知识库版本。 |
| FR-M05-07 | 老人可以纠正识别错误，但纠正不能自动消除风险，必须重新执行核查。 |
| FR-M05-08 | 同一药物在不同剂型、剂量和给药方式下不得只按药名合并判断。 |

#### 验收标准

- 低置信 OCR、识别失败或来源缺失时，不能出现“可以服用”的肯定结论。
- 已知高危场景中，无论 Prompt 如何诱导，系统均不输出具体调剂量或补服方案。
- 风险结果页能够清楚显示“为什么触发”“来源是什么”“下一步找谁”。
- 家属端只收到与本次风险相关的摘要，不接收完整原始对话。

### 5.6 M06 提醒与漏服处理

#### 模块目标

在正确的时间提醒老人服药，记录真实服药状态，并在漏服时给出有来源、与风险匹配的处理路径。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M06-01 | 每个用药计划支持多个时间窗口、按天/周频次、起止日期、饭前饭后关系和临时调整。 |
| FR-M06-02 | 提醒支持系统推送、页面语音、大字、高对比和可用的震动/屏幕高亮。 |
| FR-M06-03 | 页面关闭或浏览器未打开时，通过后端自动任务和系统级通知保障提醒；必要时可配置短信或语音提醒通道。 |
| FR-M06-04 | 每个用药窗口最多发送两条常规提醒，避免警报疲劳。 |
| FR-M06-05 | 老人可以记录“已服用”“稍后提醒”“没有服用”“我不确定”。 |
| FR-M06-06 | 超过提醒窗口但未操作时，状态先记为“尚未确认”，不得直接标记为漏服。 |
| FR-M06-07 | 老人明确选择“没有服用”后，才进入漏服处理页面。 |
| FR-M06-08 | 漏服处理必须区分低风险与高风险药物，并显示信息来源。 |
| FR-M06-09 | 没有可靠漏服规则时，提示不要自行补服或加倍服用，并联系医生/药师。 |
| FR-M06-10 | 提醒与服药记录在本地和云端保留一致的时间、状态和修改历史。 |

#### 提醒卡片

首屏显示：

- 到时间了；
- 药名；
- 剂量；
- 服用时间；
- 大白话用法；
- “已经吃啦”；
- “等会儿提醒”。

次级入口：

- “没有服用”；
- “我不确定”；
- “问一下”；
- “联系家人”。

#### 验收标准

- 老人点击“稍后提醒”后，系统不把本次记录判为漏服。
- 页面关闭时，已授权且通知权限正常的设备仍可收到系统级提醒。
- 高热风险场景下，漏服页不生成具体补服时间或剂量。
- 修改未来计划不会改变历史服药记录。

### 5.7 M07 适老化前端与交互

#### 模块目标

确保老年人在视觉、听觉、认知和精细操作能力下降的情况下，仍能完成核心任务。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M07-01 | 老人端正文不小于 18pt，关键标题和信息进一步放大。 |
| FR-M07-02 | 可点击区域不小于 60×60pt，按钮之间保持足够间距，减少误触。 |
| FR-M07-03 | 正文与背景对比度不低于 4.5:1；风险状态不能只靠颜色区分。 |
| FR-M07-04 | 支持浏览器缩放、系统字体放大和响应式布局，不出现内容遮挡。 |
| FR-M07-05 | 语音、点击两条通道均可用；语音失败时自动显示点击兜底。 |
| FR-M07-06 | 查看今日用药、发起语音提问和执行安全核查均不超过两步。 |
| FR-M07-07 | 默认选项必须安全，不能以倒计时自动确认“已服药”。 |
| FR-M07-08 | 表单错误使用具体说明，例如“药名旁边有一处看不清，请重拍或修改”。 |
| FR-M07-09 | 支持语音朗读当前任务、药物用法和风险提示。 |
| FR-M07-10 | 关键页面提供加载、空状态、超时、离线、无权限和错误恢复状态。 |
| FR-M07-11 | 桌面端适合家属查看摘要，移动端适合老人完成日常操作。 |

#### 验收标准

- 在 320px 宽度和常见手机尺寸下，无横向滚动、遮挡或关键内容截断。
- 核心按钮在触屏上可稳定点击，不依赖悬停。
- 语音权限被拒绝时仍能完成查看、确认和求助。
- 颜色模式变化后风险文字、图标和来源仍可辨认。

### 5.8 M08 家属协同与通知

#### 模块目标

让家属在真正需要时介入，同时保持老人的知情权、共享控制权和隐私。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M08-01 | 支持老人创建家属邀请，并由老人确认角色和权限。 |
| FR-M08-02 | 支持至少“只读摘要”和“紧急联系”两类权限。 |
| FR-M08-03 | 家属与老人通过账号关系绑定，数据通过加密云端同步。 |
| FR-M08-04 | 仅在多次未确认、高危风险、主动求助或预设条件满足时通知家属。 |
| FR-M08-05 | 通知前根据老人设置执行权限判断，并向老人显示已通知的摘要。 |
| FR-M08-06 | 家属端展示风险详情、当前药物、原因和协助方式，不展示完整原始对话。 |
| FR-M08-07 | 家属可纠正 OCR、补充药物信息、查看复诊摘要和处理风险提醒。 |
| FR-M08-08 | 家属默认不能代替老人修改处方、确认老人已服药或关闭高危警告。 |
| FR-M08-09 | 老人可以随时调整共享范围、撤销邀请或叫停异常通知。 |
| FR-M08-10 | 通知通道支持系统级推送；必要时支持短信或语音电话，并显示发送结果。 |

#### 家属摘要内容

- 本周已服、未确认和明确未服次数；
- 当前高危事项；
- 最近主动求助；
- 当前药物与过敏史；
- 复诊前需要核实的药物；
- 数据同步时间。

#### 验收标准

- 老人撤销授权后，家属无法继续查看新摘要或接收新通知。
- 普通成功服药不逐条打扰家属。
- 家属看到的通知内容与老人已知情的共享范围一致。
- 异常通知具有幂等性，网络重试不会在短时间内重复发送多条相同通知。

### 5.9 M09 一键求助与紧急链路

#### 模块目标

在老人无法完成复杂对话时，提供独立于 Agent 自由生成的高优先级求助链路。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M09-01 | 支持屏幕 SOS、“我不舒服”语音入口；预留物理按钮或外部设备触发接口。 |
| FR-M09-02 | 语音识别到“我不舒服”“头晕得很”等表达时，进入危险信号识别，不先进行普通问药回答。 |
| FR-M09-03 | 触发 SOS 后展示老人关键信息：当前主要药物、过敏史、紧急联系人、求助时间。 |
| FR-M09-04 | 按预设顺序通知家属、照护者和紧急联系人，并记录送达状态。 |
| FR-M09-05 | 提供 120/110 明显的一键拨号入口。 |
| FR-M09-06 | Web 页面不得宣称能够静默自动拨打 120/110；若接入外部语音服务，必须经过合规和可用性验证。 |
| FR-M09-07 | SOS 不依赖大模型正常返回；AI 服务不可用时仍应显示联系人、急救信息和拨号入口。 |
| FR-M09-08 | 求助事件、通知对象、发送结果和取消记录写入审计日志。 |

#### 验收标准

- 断网或 AI 服务超时时，SOS 页面仍能打开并显示联系人信息。
- 家属能够收到求助摘要和老人当前用药/过敏信息。
- 120/110 的交互必须明确表达为“拨打”，不得误导为系统已代为呼叫。

### 5.10 M10 信任边界、隐私与审计

#### 模块目标

让用户知道系统能做什么、为什么这样回答、数据存在哪里，并能纠正、共享、导出和删除数据。

#### 功能要求

| 编号 | 需求 |
|---|---|
| FR-M10-01 | 明确声明系统不提供疾病诊断，不修改处方，不替代医生和药师。 |
| FR-M10-02 | 对诊断、调剂量、停药等越界请求直接拒答，并给出下一步。 |
| FR-M10-03 | 高风险输出使用预审模板和工具白名单，避免自由生成绕过。 |
| FR-M10-04 | 老人或家属可以一键纠正 OCR、药名、剂量、频次、来源和共享设置。 |
| FR-M10-05 | 关键纠正、风险核查、通知、授权变化和 SOS 均记录审计日志。 |
| FR-M10-06 | 本地敏感数据加密保存；云端同步使用传输加密和静态加密。 |
| FR-M10-07 | 老人可以查看、导出和删除个人档案；删除需要覆盖本地与云端，并提供完成状态。 |
| FR-M10-08 | 采集语音、图片和健康数据前提供目的说明和权限选择。 |
| FR-M10-09 | 使用第三方模型或通知服务时，明确数据范围、服务提供方和保留策略。 |
| FR-M10-10 | 防止外部文档、图片文字和网页内容通过 Prompt Injection 改变系统安全规则。 |
| FR-M10-11 | 日志不记录不必要的密码、密钥、完整敏感图片或完整医疗对话。 |

#### 验收标准

- 普通对话无法诱导 Agent 输出处方修改。
- 用户能够定位并纠正一条已进入档案的错误药名。
- 删除完成后，本地缓存和云端档案均不可再访问。
- 家属通知、老人授权与审计记录可以相互对应。

## 6. 核心业务流程

### 6.1 首次建档

1. 用户选择老人或家属角色。
2. 创建老人档案，填写疾病、过敏史和身体偏好。
3. 通过拍照、语音或手动方式添加当前药物。
4. 每项药物完成字段确认。
5. 添加家属和紧急联系人。
6. 设置通知方式与共享范围。
7. 执行一次通知测试。
8. 展示能力边界并进入老人首页。

### 6.2 新增药物与相互作用核查

1. 老人拍摄药盒、说明书或处方单。
2. 系统保存原图并执行 OCR。
3. 系统展示字段化识别结果和低置信提醒。
4. 老人或家属确认/修改关键字段。
5. Agent 读取当前用药、疾病、过敏史和药物成分。
6. 系统执行重复成分、相互作用和禁忌核查。
7. 系统检索来源并计算风险等级。
8. 低危输出解释和来源；中危要求补充信息或联系专业人员；高危停止具体建议。
9. 老人确认后写入用药档案。
10. 需要时生成家属异常摘要。

### 6.3 语音问药

1. 老人按住说话。
2. 语音转写为文本并显示。
3. Agent 识别意图和涉及药物。
4. 系统核查当前完整用药档案。
5. 必要时请求补拍或确认药名。
6. 执行 RAG 和风险规则。
7. 输出结论、下一步、原因和来源。
8. 老人可以展开来源、纠错或请求联系家人。

### 6.4 服药提醒

1. 后端定时任务识别到服药窗口。
2. 推送系统通知，页面内同时准备大字、语音和触觉反馈。
3. 老人选择“已服用”“稍后提醒”“没有服用”或“我不确定”。
4. 系统立即持久化并同步状态。
5. 超时未操作时记录为“尚未确认”。
6. 明确未服后进入风险匹配的漏服处理。
7. 达到异常条件时通知授权家属。

### 6.5 身体不适

1. 老人触发“我不舒服”或描述症状。
2. 系统先识别紧急危险信号。
3. 存在紧急信号时进入 SOS。
4. 非紧急情况下询问发生时间、表现和近期药物变化。
5. 系统结合当前药物进行安全核查，但不作诊断。
6. 输出求助建议、需要观察的内容和可提供的用药摘要。

### 6.6 数据纠正

1. 用户发现药名、剂量或来源错误。
2. 进入原记录并修改字段。
3. 系统显示修改前后差异。
4. 重新执行相关风险核查。
5. 保存新版本和审计记录。
6. 同步到老人端和授权家属端。

## 7. 数据需求

### 7.1 核心数据对象

|---|---|

| IntakeDocument | 图片、文件类型、上传时间、关联药物 |
| OCRResult | 字段、置信度、原文、确认状态、修正记录 |
| RiskCheck | 输入药物快照、风险等级、触发因素、规则版本 |
| KnowledgeSource | 说明书/处方/规则、版本、审核状态、来源类型 |
| Conversation | 用户输入、AI 输出、涉及药物、来源、风险等级 |

| ConsentGrant | 共享对象、共享范围、有效期、撤销状态 |

| SOSRecord | 触发方式、时间、联系人、通知结果、拨号入口状态 |

### 7.2 数据优先级

关键数据包括：

- 当前用药与剂量；
- 药物过敏和严重不良反应；
- 紧急联系人；
- 风险核查结果；
- 服药状态；
- 老人授权；
- 数据来源和审计记录。

### 7.3 本地持久化

- 使用浏览器持久化存储保存用药档案、草稿、图片元数据和操作状态。
- 存储结构必须带版本号和迁移机制。
- 页面刷新、意外关闭和浏览器重启后能够恢复。
- 上传中的图片和未完成的 OCR 确认必须作为草稿保存。
- 存储空间不足时先保护已验证的健康档案，再提示清理缓存。
- 用户执行删除时，需要清理本地数据和待同步操作。

### 7.4 跨设备同步

- 采用本地优先、云端同步架构。
- 同步记录使用稳定 ID 和版本号，避免重复创建。
- 关键数据冲突时保留双方版本，不静默覆盖医疗信息。
- 同步失败显示“尚未同步”，并支持重试。
- 家属端只能读取被授权范围内的数据。

## 8. AI 与技术方案约束

### 8.1 能力链路

```text
Web / PWA 适老化前端
  ├─ 相机与图片持久化
  ├─ 语音输入与语音播报
  ├─ 大字与全屏提醒
  └─ 页面级风险状态
          │
          ▼
Agent 编排层
  ├─ 意图识别
  ├─ 任务规划
  ├─ 工具白名单
  ├─ 风险策略
  └─ 回答模板
          │
          ├─ OCR / 多模态识别
          ├─ 用药档案工具
          ├─ RAG 检索
          ├─ 风险规则引擎
          ├─ 家属通知工具
          └─ 审计记录
          │
          ▼
本地持久化 + 加密云端同步 + 定时任务与通知
```

### 8.2 比赛要求对应

| 比赛考察点 | 本项目落点 |
|---|---|
| 大模型集成质量 | 首句结论、结构化输出、稳定语气、风险模板、纠错 |
| Agent/工作流 | 多步骤任务拆解、工具调用、风险分支、独立通知和 SOS 链路 |
| RAG | 药品说明书、处方、相互作用和漏服规则检索与来源卡片 |
| 多模态 | 药盒/说明书/处方拍照、OCR、语音转写和语音播报 |
| AI 安全与可控性 | 高危拦截、资料不足拒绝、来源约束、越界拒答、审计 |
| MCP/工具集成 | 文件、会话、RAG、档案、通知和风险工具受控接入 |
| 前端工程质量 | 组件化、响应式、状态管理、本地持久化和错误边界 |
| 用户体验 | 语音优先、拍照录入、结论先行、大字大按钮、全屏提醒 |

### 8.3 DSH 集成落点

以下名称作为需求阶段的技术集成占位，正式实现前需核对实际包、版本和接口：

- `dsh-open-file`：打开文件与文件选择；
- `dsh-file-resource`：文件资源持久化与访问；
- `dsh-session-media`：会话中的图片、音频等媒体；
- `@kai232/dsh-rag`：RAG 检索与来源返回；
- DSH 内核、System Prompt、工具白名单和策略层：Agent 编排与高风险限制；
- 定时任务和通知插件：关闭页面后的提醒与家属通知。

### 8.4 技术边界

- 浏览器不能保证直接静默拨打 120/110。
- 关闭页面后的可靠提醒依赖 PWA、系统推送权限和后端定时任务。
- iOS、桌面浏览器和不同系统上的震动、灯光和通知权限存在差异，必须有降级方案。
- 纯本地存储无法满足跨设备家属协同，必须使用后端同步。
- 商用 AI API 和短信/语音服务费用由参赛团队承担，密钥不得进入公开仓库。

## 9. 非功能需求

### 9.1 可访问性

- 正文≥18pt，关键标题进一步放大；
- 对比度≥4.5:1；
- 触控区域≥60×60pt；
- 支持键盘焦点、屏幕阅读器标签和非颜色状态提示；
- 语音不可用时不影响查看、确认和求助；
- 不设置自动关闭且会确认危险操作的通知。

### 9.2 性能

- 老人端首屏优先展示本地可用信息。
- 大模型未返回前，先显示已确认的用药清单和安全状态。
- AI 请求显示真实处理阶段和可取消/重试状态。
- 图片在本地压缩后再同步，保留可读性。
- 页面切换不丢失拍摄和确认草稿。

### 9.3 可靠性

- 本地写入完成后才提示“已保存”。
- 云端未同步时明确展示同步状态。
- 通知发送具有幂等性，避免重复轰炸。
- 服务超时不影响 SOS、联系人信息和已确认用药查看。
- 关键错误必须有用户可执行的恢复路径。

### 9.4 安全与隐私

- API 密钥只通过环境变量配置。
- 健康数据在传输和静态存储时加密。
- 最小权限访问，家属不能越权读取未共享内容。
- 导出和删除作用于本地与云端。
- 防止跨站脚本、文件上传滥用、提示词注入和越权接口。
- 日志脱敏，不保留无关敏感原始内容。

### 9.5 兼容性

- 支持主流现代浏览器；
- 支持手机和桌面响应式布局；
- PWA 支持安装、离线缓存和推送能力；
- 对不支持震动、灯光或后台推送的设备显示替代路径。

## 10. 验收场景

### 场景 A：拍照添加新药

老人拍摄新药药盒，OCR 将药名识别错误。系统将低置信字段标红，老人点击纠错并确认。系统读取现有用药后提示成分重复，进入中危状态并建议联系医生。老人关闭页面后重新打开，仍能看到识别原图、修正后的药名和未完成的风险处理。

### 场景 B：普通相互作用查询

老人说“这个药能不能一起吃”。系统识别语音，追问具体药物并读取完整用药清单。核查完成后首屏显示结论和风险等级，第二层显示涉及的药物、说明书来源和仍需补充的信息。

### 场景 C：高危药物漏服

老人收到华法林提醒后未操作。系统先记“尚未确认”，再次提醒后老人选择“没有服用”。系统不输出自行补服方案，提示不要加倍服用，并显示联系医生/药师和通知家属的入口。

### 场景 D：页面关闭后的提醒

老人关闭浏览器。后端定时任务到达服药时间后，通过已授权系统通知通道提醒老人；家属仅在满足异常条件时收到摘要通知。

### 场景 E：家属跨设备协同

老人用手机确认药物后，家属在另一台设备登录并获得授权，能够看到当前药物、过敏史和风险摘要，但看不到老人完整原始对话。

### 场景 F：头晕求助

老人说“我头晕，是不是药的问题”。系统先识别危险信号；不存在紧急表现时，询问发生时间和近期用药变化，结合当前用药进行核查，不作疾病诊断。出现严重症状时直接进入 SOS。

### 场景 G：纠错与审计

家属发现药名识别错误，修改后系统重新核查风险，并记录修改人、修改时间、修改前后值和重新核查结果。

### 场景 H：删除数据

老人执行删除档案并确认。系统删除本地数据、云端档案和待同步任务，家属无法继续访问，系统显示删除完成状态。

## 14. 术语

| 术语 | 说明 |
|---|---|
| OCR | 光学字符识别，从图片中提取文字 |
| RAG | 检索增强生成，从经过审核的知识源检索后再生成回答 |
| Agent | 能进行任务拆解、工具调用和策略分支的 AI 编排实体 |
| 高危药物 | 错误停用、漏服或调整剂量可能造成严重后果的药物 |
| 尚未确认 | 提醒后老人未操作或表示“不确定”，不能直接视为漏服 |
| 本地优先 | 先保证设备本地数据持久化和恢复，再同步到云端 |
| 风险分级 | 根据证据、药物、疾病和不确定性限制 AI 可执行的回答 |
